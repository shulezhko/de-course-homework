2. Python vs SQL: два підходи до даних

Data Engineer працює з даними двома шляхами. Розуміння паралелей між ними — ключ до ефективності.

🐍 Python (Polars / Pandas)
  • Дані у пам'яті (DataFrame)
  • Процедурний / функціональний стиль
  • Eager або Lazy evaluation
  • Формати: Parquet, JSON, CSV
  • Масштаб: один вузол (до ~100GB)
🗃 SQL (DuckDB / PostgreSQL)
  • Дані в движку СУБД
  • Декларативний стиль
  • Query planner оптимізує автоматично
  • Формати: таблиці, views, Parquet (DuckDB)
  • Масштаб: залежить від движка

4. Eager vs Lazy Execution

Pandas (Eager)
# Все читається у RAM одразу
df = pd.read_parquet("trips.parquet")
# Фільтрація — після повного завантаження
result = df[df["fare"] > 0]

Кожна операція виконується негайно. Весь файл у пам'яті.

Polars (Lazy)
# Лише план — 0 байт даних!
lf = pl.scan_parquet("trips.parquet")
# Будуємо план без IO
result = lf.filter(pl.col("fare") > 0)
# IO тільки тут:
df = result.collect()

Дані читаються при .collect() з оптимізаціями.

Predicate & Projection Pushdown

Коли Polars (або DuckDB) будує план запиту, оптимізатор переміщує фільтри до рівня сканування файлу. Row groups, що не задовольняють умову (за min/max статистикою у footer), навіть не читаються.

🐍 Polars
lf = pl.scan_parquet("events.parquet")
plan = (
    lf.filter(pl.col("fare") > 0)
      .select(["pickup_dt", "fare"])
)
print(plan.explain(optimized=True))
# PARQUET SCAN [...] 
# PROJECT 2/19 COLUMNS
# SELECTION: col("fare") > 0
🗃 DuckDB SQL
EXPLAIN ANALYZE
SELECT pickup_dt, fare
FROM read_parquet('events.parquet')
WHERE fare > 0;
-- Plan показує:
-- PARQUET_SCAN [projection: 2 cols]
-- Filter: fare > 0 (pushdown)
Те саме явище — дві мови. І Polars, і DuckDB використовують Parquet footer statistics для пропуску непотрібних row groups. Різниця лише в синтаксисі.

6. ДЗ Lesson 02: ETL Pipeline (Polars)

Завдання: побудувати ETL pipeline на Polars, що перетворює годину подій GitHub Archive (NDJSON) у аналітичні Parquet-таблиці.

Task 1: Bronze — Flatten NDJSON

Суть: Розгорнути вкладений JSON у пласку таблицю. Жодної фільтрації.

def build_bronze():
    df = pl.scan_ndjson(config.LANDING_FILE, schema=config.LANDING_SCHEMA)
    bronze = df.select(
        pl.col("id").alias("event_id"),
        pl.col("type").alias("event_type"),
        pl.col("actor").struct.field("id").alias("actor_id"),
        pl.col("actor").struct.field("login").alias("actor_login"),
        pl.col("repo").struct.field("id").alias("repo_id"),
        pl.col("repo").struct.field("name").alias("repo_name"),
        pl.col("created_at").str.to_datetime("%Y-%m-%dT%H:%M:%SZ", time_zone="UTC"),
        pl.col("public"),
        pl.col("payload").struct.field("action").alias("action"),
        pl.col("payload").struct.field("commits")
            .list.len().fill_null(0).alias("commit_count"),
    ).collect()
    bronze.write_parquet(config.BRONZE_FILE)
    return bronze
Ключові прийоми: .struct.field("login") — доступ до вкладеного поля Struct; .list.len().fill_null(0) — довжина масиву комітів (для не-Push подій = null → 0).

def build_silver(bronze_df):

8. Window Functions: SQL vs Python

Window functions зберігають всі рядки (на відміну від GROUP BY, що колапсує). Це must-have для DE.

🗃 SQL (DuckDB)
-- Running total
SELECT event_date, events,
  SUM(events) OVER(
    ORDER BY event_date
  ) AS running
FROM daily;

-- Top-N per group
SELECT *, ROW_NUMBER() OVER(
  PARTITION BY event_type
  ORDER BY cnt DESC
) AS rn
QUALIFY rn <= 5;

-- Day-over-day change
SELECT event_date,
  LAG(events) OVER(
    ORDER BY event_date
  ) AS prev_day
FROM daily;
🐍 Python (Polars)
# Running total
df.with_columns(
  pl.col("events").cum_sum()
    .alias("running")
)

# Top-N per group
df.with_columns(
  pl.col("cnt")
    .rank(method="ordinal", descending=True)
    .over("event_type")
    .alias("rn")
).filter(pl.col("rn") <= 5)

# Day-over-day (shift)
df.with_columns(
  pl.col("events").shift(1)
    .alias("prev_day")
)

10. Partition Pruning

Якщо дані партиціоновані по колонці (Hive layout: event_date=2024-01-08/), движок може читати тільки потрібні партиції.

✗ Naive (сканує 14 файлів)
JOIN calendar c
  ON strftime(e.event_date)
   = strftime(c.day)
WHERE c.iso_week = 2
-- Перетворення ключа JOIN
-- блокує filter propagation
✓ Optimized (сканує 7 файлів)
JOIN calendar c
  ON e.event_date = c.day
WHERE c.iso_week = 2
-- Прямий JOIN → DuckDB пропагує
-- фільтр на партиційну колону
Правило: Ніколи не перетворюйте ключ JOIN (strftime, CAST тощо), якщо хочете partition pruning. Прямий join по сирій колоні = оптимізатор може працювати.

11. ДЗ Lesson 03: dbt Models (розбір)

Task 1: stg_events view

DQ-фільтрація сирих подій. Materialized: view — критично для наскрізного partition pruning.

{{ config(materialized='view') }}
SELECT id, event_type, created_at, event_date, actor_login, repo_name,
       payload_commit_count, payload_action, payload_ref
FROM read_parquet('{{ var("events_path") }}', hive_partitioning = true)
WHERE event_type IN ('PushEvent', 'IssuesEvent', 'PullRequestEvent',
                       'WatchEvent', 'IssueCommentEvent')
  AND actor_login NOT LIKE '%[bot]'
  AND NOT (event_type = 'PushEvent' AND payload_commit_count = 0)

Task 2: repo_top_events QUALIFY

SELECT event_type, repo_name,
  COUNT(*) AS event_count,
  ROW_NUMBER() OVER(PARTITION BY event_type ORDER BY COUNT(*) DESC, repo_name) AS type_rank
FROM {{ ref('stg_events') }}
GROUP BY event_type, repo_name
QUALIFY type_rank <= 5

Task 5: starred_repos_without_push Anti-Join

SELECT DISTINCT w.repo_name
FROM {{ ref('stg_events') }} w
WHERE w.event_type = 'WatchEvent'
  AND NOT EXISTS (
    SELECT 1 FROM {{ ref('stg_events') }} p
    WHERE p.event_type = 'PushEvent' AND p.repo_name = w.repo_name
  )
Чому NOT EXISTS, а не NOT IN? NOT IN з підзапитом, що містить NULL, повертає пустий результат. NOT EXISTS — безпечний завжди.
